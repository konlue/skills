# Coldreview · 代码自审

> 刚才那段代码是「你」写的。现在换个人来审它：只查四件事，只出清单，不动手改。

你刚写完（或即将提交）一段代码。现在切换角色：**资深 Reviewer**，不是作者。

## 为什么需要这一轮

同一次会话里，写代码的人和审代码的人是同一个模型，天然会为自己的实现辩护——「我这么写是因为……」，于是真正的漏洞被合理化掉。

破解办法只有三条：**换角色、禁止动手改、限定只查四件事**。少了任何一条，这一轮都会退化成「再检查一遍」，基本查不出东西。

## 硬规则

1. **只审不改。**
   这一轮不修改任何文件、不输出完整替换后的文件。只输出问题清单 + 最小修改方案。要改，等用户点头后再另起一轮。
2. **只查这四件事。**
   边界条件、异常处理、性能瓶颈、安全风险。不评论命名、格式、风格、架构品味——那些塞进末尾的「可选优化」，不占严重程度分级。
3. **每个问题必须能落地。**
   缺任何一项就不算一个问题：**位置**（文件:行号）、**为什么是问题**（触发条件 + 后果）、**最小改法**（可直接粘上去的代码片段）。
4. **没问题就直说没问题。**
   不为了显得认真而凑数。四件事各自给结论，包括「未发现」。

## 检查什么（四件事）

**① 边界条件** —— 什么输入会让它出错

- 空值 / 空字符串 / 空集合 / 空对象
- `0`、负数、极大极小值、浮点精度
- 数组首尾元素、单元素、超长输入
- 分页 / 限流的边界（offset 越界、size 为 0）
- 时间边界（时区、跨天、闰年、夏令时）
- 并发下的竞态与重复提交

**② 异常处理** —— 出错时会发生什么

- 异常被吞掉（`catch {}`、空 `except`）
- `catch` 范围过宽，把不该吞的也吞了
- 资源没释放（文件句柄、数据库连接、锁、定时器）
- 失败后状态不一致（改了一半没回滚、中间态被读到）
- 重试不幂等、重试风暴
- 错误信息泄露内部细节（堆栈、SQL、路径）

**③ 性能瓶颈** —— 量大了会怎样

- 循环里的 IO（数据库查询、HTTP 请求、文件读写）
- N+1 查询、缺索引的全表扫描
- 不必要的全量遍历 / 全量拷贝
- 热路径上的同步阻塞、串行等待可以并行的操作
- 无界增长：缓存不淘汰、日志不打滚、数组只增不减
- 大对象被意外保留（闭包、全局、监听器未解绑）

**④ 安全风险** —— 有人恶意利用会怎样

- 外部输入未校验 / 未转义（SQL 注入、XSS、命令注入、路径穿越）
- 越权：没校验资源归属，改个 id 就能看别人的数据
- 敏感信息进日志或返回给前端（密码、token、身份证）
- 密钥硬编码
- 上传文件未限制类型 / 大小 / 路径
- 依赖存在已知漏洞

> 更细的检查点见仓库里的 `CHECKLIST.md`（可选，不影响本轮执行）。

## 工作流

**Step 1 确定范围**
明确要审的是什么：本次改动（`git diff`）、指定文件、还是刚写完的那段实现。范围不清就先问。

**Step 2 切换角色**
作者身份作废。假设这段代码是你不认识的同事写的，而你要为它上线后的事故负责。

**Step 3 逐项扫描**
按四件事过一遍。对每个位置问的是「**什么输入、什么时序下它会出错**」，不是「它写得优不优雅」。

**Step 4 输出清单**
按严重程度分级，格式见下。

**Step 5 给结论**
结尾必须给一句可执行的判断：能提交 / 修完 N 个问题再提交 / 需要重做。

## 输出格式

````markdown
## 自审结果：src/api/user.ts

**结论**：建议修完 2 个 🟡 再提交

### 🔴 严重（阻塞提交）

**1. `src/api/user.ts:42` — id 为空时直接 500**
- 为什么：`id` 未经校验就传给 `findById`，空值时抛异常，整个请求失败
- 最小改法：
  ```ts
  if (!id) return res.status(400).json({ error: 'missing id' })
  ```

### 🟡 重要
（同上格式）

### 🔵 建议
### ⚪ 可选（不影响提交）

**逐项结论**

| 检查项 | 结果 |
|--------|------|
| 边界条件 | 1 🔴 1 🟡 |
| 异常处理 | 未发现 |
| 性能瓶颈 | 1 🔵 |
| 安全风险 | 未发现 |
````

分级标准：

| 级别 | 含义 | 处理 |
|------|------|------|
| 🔴 严重 | 会崩溃、数据出错、安全漏洞、不可逆后果 | 阻塞提交 |
| 🟡 重要 | 特定输入或场景下会出错、明显性能问题 | 建议提交前修掉 |
| 🔵 建议 | 有改进空间，不影响正确性 | 可跟进 |
| ⚪ 可选 | 风格、命名、可读性 | 想改再说 |

## 关键提醒

- **别复述代码做了什么。** 用户知道自己写了什么，他要的是哪里会出问题。
- **改法要「最小」。** 给能直接粘上去的几行，不要给重构方案。真想重构就单独提一句，别混在自审里。
- **不确定就标「待验证」。** 拿不准某个问题是否真的成立（比如不确定上游会不会传空值），如实标注，不要用确定的语气编造。
- **改完可以再来一轮。** 修掉 🔴🟡 后重新扫一遍，确认没引入新问题。

## 什么时候跳过

- 改动只是文档、注释、格式化
- 纯配置改动，且不涉及外部输入
- 一次性 demo、临时脚本
- 用户明确说「直接提交」

这时最多回一句「本次改动无需自审」，不要走完整流程。

## 与其他 skill 的配合

- **minipatch** 管「改之前」：先报计划，只改该改的
- **coldreview** 管「改之后」：提交前换角色审一遍

两者不冲突，可以按 minipatch 改、按 coldreview 审。

## 验收标准

- 输出的是问题清单，不是一个改好的文件
- 每个问题都带位置、原因、最小改法，三者缺一不算数
- 四件事都给了结论，包括「未发现」
- 没有把命名、格式、风格问题算进严重程度分级
