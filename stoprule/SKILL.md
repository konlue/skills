# Stoprule · 知道什么时候该停

> 真正专业的优化，不是无限追求更快，而是知道什么时候该停。

## 为什么需要这一条

「继续优化」是一条没有终点的指令。AI 会一直改下去，每一轮都能拿出「新的改进」——但收益越来越小、改动越来越大、风险越来越高。最后你拿到一个改了 20 处、性能提升 2%、还带了两个新 bug 的 PR。

根因是三个东西同时缺失：**基线**（不知道从哪开始）、**目标**（不知道到哪算够）、**阈值**（不知道什么样的收益值得做）。

## 硬规则

1. **先建基线，再动手。**
   优化前的真实数据是多少？用什么方法测的？测了几次？没有基线，后面所有「提升了 40%」都是自我感觉。
2. **先定目标和测量方法。**
   到什么数值算达标？目标要有来源（产品要求 / SLA / 竞品 / 体感阈值），不能拍脑袋。达标前后必须用**同一个方法、同一个环境**测。
3. **收益超过成本阈值才实施。**
   收益要落在数字上，成本不只是时间——还有改动面、新增复杂度、后续维护、引入的依赖和风险。
4. **不到阈值就停止，并记录取舍。**
   停止不等于没做事。把「试过什么、预期收益多少、为什么放弃」写下来，这份记录和下一段优化代码一样有价值。
5. **每轮结束重新测量。**
   用数据确认是否真的变好了，不靠「应该快了吧」。没变好就回滚这一轮。
6. **达标即停，不追加。**
   触发停止条件后不再「顺手再优化一下」。想继续，就重新走一遍流程、重设目标。

## 停止条件模板

动手前先把这张表填出来：

```markdown
### 优化任务：<优化什么>

**基线**（优化前实测，不是估算）

| 指标 | 当前值 | 测量方法 | 测量环境 |
|------|--------|----------|----------|
| P95 响应时间 | 820ms | wrk -t4 -c100 -d30s，取 3 次中位数 | 8C16G 容器，10 万行数据 |

**目标**
- P95 ≤ 300ms（来源：产品要求的页面秒开预算）

**成本阈值**（满足其一才实施）
- 预期收益 ≥ 剩余差距的 20%
- 收益 / 改动成本 ≥ 3（成本 = 改动文件数 + 新增复杂度 + 后续维护）

**停止条件**（触发任一即停，并记录）
- [ ] 达标：P95 ≤ 300ms
- [ ] 收益不足：最优候选方案预期收益 < 50ms
- [ ] 成本超限：需改 5 个以上文件，或要引入新依赖
- [ ] 风险过大：会改变对外行为、需要数据迁移、无法快速回滚
- [ ] 边际递减：连续两轮提升 < 5%
- [ ] 时间预算用尽：投入超过 N 小时
```

## 工作流

**Step 1 建基线**
先测量当前真实数据。测不出来就先搭测量方法——**没有基线的优化等于盲改**。

**Step 2 定目标**
目标要能回答「为什么是这个数」。答不上来，说明目标本身就是错的，先去问清楚。

**Step 3 定停止条件**
从模板里勾：达标 / 收益不足 / 成本超限 / 风险过大 / 边际递减 / 时间到。

**Step 4 排候选方案**
按「预期收益 ÷ 成本」从高到低排序，从最高的开始做。先做性价比高的，往往做完前两个就达标了。

**Step 5 逐个实施并复测**
每轮做一件事，做完立刻用同一方法复测，记录前后对比。没变好的回滚掉。

**Step 6 判断停止**
触发任一停止条件就停，输出优化报告 + 取舍记录。

## 输出格式

```markdown
**结论**：达标 / 未达标（原因）/ 停止（原因）

| 轮次 | 改动 | 优化前 | 优化后 | 收益 | 决定 |
|------|------|--------|--------|------|------|
| 1 | 给 user_id 加索引 | 820ms | 410ms | -410ms | 保留 |
| 2 | 热点数据加缓存 | 410ms | 380ms | -30ms | 保留 |
| 3 | 改并发模型 | 380ms | 375ms | -5ms | **回滚**（1.3%，复杂度上升） |

**停止原因**：第 3 轮收益 5ms（1.3%），低于 5% 阈值，触发「边际递减」。

**未采用的方案及原因**

- 引入 Redis 集群：预期再降 40ms，但新增依赖 + 运维成本，成本远超收益
- 用 Rust 重写：预期降 100ms，工期 2 周，超出时间预算

**回滚了什么**：第 3 轮并发模型改动已回滚，代码回到轮次 2 的状态。
```

## 常见的「假收益」

别被这些骗了：

- **只测一次 / 只报最好的那次** → 应多次取中位数或 P95
- **冷启动和热态混在一起** → 分开测，说明测的是哪种
- **数据量不真实** → 本地 100 条跑出 1ms，线上 100 万条是另一回事
- **只看平均不看长尾** → P50 好看、P99 崩了，用户体感照样差
- **优化了一个次要指标** → QPS 上去了，内存涨 3 倍、GC 更频繁
- **在开发环境测** → 本机 M3 和生产 2C4G 完全是两回事
- **把「代码变短了」当成「变快了」** → 拿数据说话

## 什么时候不适用

- **修正确性 bug**：那不是优化，没有「够好就行」
- **修安全漏洞**：必须修完，不设阈值
- **一次性脚本、临时代码**：不值得为它建基线

## 验收标准

- 优化前先有基线数据，而不是凭感觉说「这里慢」
- 目标数值有明确来源
- 每轮改动都有前后对比数据
- 触发停止条件就真的停了，没有「再顺手改一点」
- 停止时留下取舍记录：试过什么、放弃了什么、为什么
